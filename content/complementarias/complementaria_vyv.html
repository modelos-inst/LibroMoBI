Complementaria Semana 13: Verificación y validación de modelos de simulación#

La semana pasada ajustamos distribuciones a datos reales y comprobamos, con pruebas de bondad de ajuste, que eran compatibles con ellos. Con esas distribuciones ya podemos alimentar un modelo de colas. Pero antes de usar ese modelo para tomar decisiones hay que responder dos preguntas más, que suenan parecidas y no lo son:

  • ¿El código hace lo que quisimos que hiciera? Eso es verificar.

  • ¿Lo que quisimos hacer representa el sistema real? Eso es validar.

Hoy trabajamos las dos sobre una cola M/M/s (con \(s\) servidores, no solo uno) y sobre los registros de una sucursal bancaria.

Objetivo de hoy#

Al final de la sesión deberías poder tomar un modelo de simulación, someterlo a una serie de pruebas de verificación y contrastarlo con datos del sistema real, sabiendo en cada momento cuál de las dos cosas estás haciendo y qué te permite concluir.

Convenciones utilizadas#

  • \(\lambda\): tasa de llegadas (clientes por minuto).

  • \(\mu\): tasa de servicio por servidor; \(1/\mu\) es el tiempo medio de servicio.

  • \(s\): número de servidores (igual que en las semanas 5 y 12).

  • \(\rho = \lambda/(s\mu)\): utilización por servidor. El sistema es estable si \(\rho < 1\).

  • \(W_q\), \(W\): tiempo promedio en cola y en el sistema (promedios sobre clientes).

  • \(L_q\), \(L\): número promedio en cola y en el sistema (promedios sobre el tiempo).

  • \(P(\text{espera})\): probabilidad de que un cliente tenga que hacer fila.

  • \(T\): horizonte de simulación; \(R\): número de réplicas; HW: semiancho (half-width) de un intervalo de confianza.

2. El modelo M/M/s que vamos a revisar#

Supuestos del modelo conceptual#

Los escribimos explícitamente porque son la base de todo lo que sigue: la verificación revisa que el código los respete y la validación revisa que la realidad los respete.

  1. Las llegadas siguen un proceso de Poisson con tasa \(\lambda\) (interarribos exponenciales, semana 6).

  2. Los tiempos de servicio son exponenciales con tasa \(\mu\) por servidor.

  3. Hay \(s\) servidores idénticos, disponibles todo el tiempo.

  4. Una sola fila, disciplina FCFS (first come, first served): se empieza a atender en orden de llegada. En las semanas 4 y 5 la llamamos FIFO; con un servidor es lo mismo, pero con varios el nombre preciso es FCFS, porque se garantiza el orden en que los clientes empiezan a ser atendidos, no el orden en que salen.

  5. Capacidad ilimitada; nadie abandona la fila.

  6. El sistema arranca vacío.

El código#

Partimos del simulador simular_mms de la semana 5 (el que mide \(W_q\) y \(W\) sobre clientes y \(L\), \(L_q\) por área bajo \(N(t)\)) y le agregamos cuatro cosas que vamos a necesitar para revisarlo:

  • traza=True devuelve dos tablas: una fila por cliente atendido y una fila por evento.

  • interarribo y servicio permiten reemplazar las exponenciales por cualquier otra función. Así podemos inyectar tiempos fijos y probar el mismo código, sin hacer una copia.

  • n_max limita cuántos clientes llegan, útil para casos pequeños que se pueden calcular a mano.

  • pausa hace que un servidor se retire durante un intervalo. Se usa solo en la sección 4; por ahora ignóralo.

Usamos simpy.PriorityResource en lugar del simpy.Resource de las semanas 4 y 5. Como todos los clientes piden el servidor con la misma prioridad, la fila sigue siendo FCFS y el modelo se comporta exactamente igual. La prioridad solo entra en juego con el descanso; la explicamos en la sección 4.4, cuando lo usemos.

Cómo leer el código. Para que sea fácil compararlo con el de la semana 5, los comentarios marcan las diferencias:

def simular_mms(lam, mu, s, T, semilla=0, interarribo=None, servicio=None,
                n_max=None, pausa=None, traza=False):
    # Simula una cola M/M/s y devuelve las métricas de desempeño: el modelo de la semana 5, ampliado.
    #   lam: tasa de llegadas    mu: tasa de servicio por servidor
    #   s:   número de servidores    T: horizonte de simulación
    # NUEVO: parámetros opcionales. Si no se usan, el modelo es idéntico al de la semana 5.
    #   interarribo, servicio : funciones f(rng) que devuelven un tiempo. Sirven para probar
    #                           el mismo código con tiempos fijos (sección 3.2).
    #   n_max                 : número máximo de clientes que llegan (None = sin límite)
    #   pausa                 : (inicio, fin) -> un servidor se retira en ese intervalo (sección 4.4)
    #   traza                 : si es True, devuelve además la tabla de clientes y la de eventos
    rng = np.random.default_rng(semilla)

    # NUEVO: tiempos por defecto. Son los mismos rng.exponential(...) de la semana 5,
    # escritos como funciones para poder reemplazarlos desde afuera por otros tiempos.
    def interarribo_exponencial(rng):
        return rng.exponential(1 / lam)

    def servicio_exponencial(rng):
        return rng.exponential(1 / mu)

    if interarribo is None:              # si no nos pasan una función, usamos la exponencial
        interarribo = interarribo_exponencial
    if servicio is None:
        servicio = servicio_exponencial

    m = {
        "llegadas": 0,                   # NUEVO: cuántos clientes llegaron (prueba de conservación)
        "salidas": 0,
        "Wq": [], "W": [],               # se promedian sobre CLIENTES
        "area_L": 0.0, "area_Lq": 0.0,   # se promedian sobre el TIEMPO
        "n_sist": 0, "n_cola": 0,        # contadores instantáneos
        "t_ult": 0.0,                    # instante del último cambio
    }
    clientes = []   # NUEVO: una fila por cliente atendido (llegada, inicio, fin, servicio, espera)
    eventos = []    # NUEVO: una fila por evento (llega, inicia servicio, sale); solo si traza=True

    def actualizar_areas(env):
        dt = env.now - m["t_ult"]
        m["area_L"] += m["n_sist"] * dt
        m["area_Lq"] += m["n_cola"] * dt
        m["t_ult"] = env.now

    def anotar(env, cid, evento):
        # NUEVO: si traza=True, guarda qué pasó, a qué cliente y cómo quedó el sistema
        # (clientes en servicio y en cola) justo después de ese evento.
        if traza:
            eventos.append({"t": env.now, "cliente": cid, "evento": evento,
                            "en_servicio": m["n_sist"] - m["n_cola"], "en_cola": m["n_cola"]})

    def cliente(env, cid, servidores):                # CAMBIO: recibe cid, el número del cliente
        t_llegada = env.now
        actualizar_areas(env)                         # cerrar el rectángulo anterior...
        m["n_sist"] += 1; m["n_cola"] += 1            # ...y recién ahí actualizar
        anotar(env, cid, "llega")

        with servidores.request(priority=1) as turno:  # CAMBIO: priority=1 (ver sección 4.4)
            yield turno                               # espera en la cola
            actualizar_areas(env)
            m["n_cola"] -= 1                          # sale de la cola, entra a servicio
            t_inicio = env.now                        # CAMBIO: se guarda el inicio para la tabla de clientes
            anotar(env, cid, "inicia servicio")

            # CAMBIO: antes rng.exponential(1 / mu). Ahora el tiempo depende del parámetro `servicio`:
            # es la exponencial por defecto, o la función que se pase al llamar simular_mms.
            t_serv = servicio(rng)
            yield env.timeout(t_serv)

        actualizar_areas(env)
        m["n_sist"] -= 1                              # abandona el sistema
        anotar(env, cid, "sale")

        m["Wq"].append(t_inicio - t_llegada)          # espera en cola
        m["W"].append(env.now - t_llegada)            # tiempo total en el sistema
        m["salidas"] += 1
        # NUEVO: la fila de este cliente en la tabla de clientes (sección 3)
        clientes.append({"cliente": cid, "llegada": t_llegada, "inicio": t_inicio,
                         "fin": env.now, "servicio": t_serv, "espera": t_inicio - t_llegada})

    def generador(env, servidores):
        cid = 0                                       # CAMBIO: numeramos a los clientes 1, 2, 3, ..., como en la semana 4
        while n_max is None or cid < n_max:           # CAMBIO: antes while True; ahora puede parar en n_max
            # CAMBIO: antes rng.exponential(1 / lam). Ahora el tiempo depende del parámetro `interarribo`:
            # es la exponencial por defecto, o la función que se pase al llamar simular_mms.
            yield env.timeout(interarribo(rng))
            cid += 1
            m["llegadas"] += 1
            env.process(cliente(env, cid, servidores))

    def descanso(env, servidores):
        # NUEVO: el descanso de un servidor (sección 4.4). Espera hasta pausa[0], pide un servidor
        # con prioridad 0 (pasa antes que cualquier cliente de la fila), lo ocupa hasta pausa[1]
        # y, al salir del bloque with, lo devuelve.
        yield env.timeout(pausa[0])
        with servidores.request(priority=0) as turno:
            yield turno
            yield env.timeout(max(pausa[1] - env.now, 0))

    # Simulación
    env = simpy.Environment()
    servidores = simpy.PriorityResource(env, capacity=s)   # CAMBIO: antes simpy.Resource (sección 4.4)
    env.process(generador(env, servidores))
    if pausa is not None:                                  # NUEVO: el descanso solo existe si se pide
        env.process(descanso(env, servidores))
    env.run(until=T)
    actualizar_areas(env)                                  # cerrar el último rectángulo

    L, Lq = m["area_L"] / T, m["area_Lq"] / T
    resultados = {
        "llegadas": m["llegadas"],                    # NUEVO
        "salidas": m["salidas"],                      # NUEVO
        "en_sistema_al_final": m["n_sist"],           # NUEVO: clientes que no alcanzaron a salir antes de T
        "utilizacion": (L - Lq) / s,                  # (clientes en servicio) / (servidores)
        "Wq": statistics.mean(m["Wq"]) if m["Wq"] else 0.0,   # CAMBIO: 0 si nadie fue atendido
        "W": statistics.mean(m["W"]) if m["W"] else 0.0,
        "Lq": Lq,
        "L": L,
        "lam_efectiva": m["salidas"] / T,
        # NUEVO: fracción de clientes que tuvo que esperar (se compara con Erlang C). Paso a paso:
        #   np.array(m["Wq"])    -> convierte la lista de esperas en un arreglo, p. ej. [0, 0.5, 0, 1.2]
        #   ... > 1e-12          -> compara cada espera: True si esperó, False si no -> [False, True, False, True]
        #   np.mean(...)         -> promedia tomando True = 1 y False = 0: (0 + 1 + 0 + 1) / 4 = 0.5
        #   float(...)           -> convierte el resultado de NumPy en un número normal de Python
        #   if m["Wq"] else 0.0  -> si nadie fue atendido la lista está vacía, y devolvemos 0
        # Se compara con 1e-12 y no con 0 por precaución: un error de redondeo diminuto no cuenta como espera.
        "P_espera": float(np.mean(np.array(m["Wq"]) > 1e-12)) if m["Wq"] else 0.0,
    }
    if traza:                                         # NUEVO: con traza devuelve también las dos tablas
        return resultados, pd.DataFrame(clientes), pd.DataFrame(eventos)
    return resultados

La referencia teórica: fórmulas de Erlang C#

Para una cola M/M/s estable existen fórmulas exactas (las de la magistral). Con \(a = \lambda/\mu\) y \(\rho = a/s\):

\[ P_0 = \left[\sum_{n=0}^{s-1}\frac{a^n}{n!} + \frac{a^s}{s!\,(1-\rho)}\right]^{-1}, \qquad P(\text{espera}) = C(s,a) = \frac{a^s}{s!\,(1-\rho)}\,P_0 \]
\[ L_q = C(s,a)\,\frac{\rho}{1-\rho}, \qquad W_q = \frac{L_q}{\lambda}, \qquad W = W_q + \frac{1}{\mu}, \qquad L = L_q + a \]

Con \(s = 1\) se recuperan las fórmulas de la M/M/1, por ejemplo \(W_q = \lambda/(\mu(\mu-\lambda))\).

def teoria_mms(lam, mu, s):
    # Métricas exactas de la M/M/s en estado estable (fórmulas de Erlang C)
    a = lam / mu
    rho = a / s
    if rho >= 1:
        return {k: float("nan") for k in ["rho", "P_espera", "Lq", "Wq", "W", "L"]}
    suma = sum(a**n / math.factorial(n) for n in range(s))
    termino_cola = a**s / (math.factorial(s) * (1 - rho))
    P0 = 1 / (suma + termino_cola)
    C = termino_cola * P0                 # probabilidad de esperar
    Lq = C * rho / (1 - rho)
    Wq = Lq / lam
    return {"rho": rho, "P_espera": C, "Lq": Lq, "Wq": Wq, "W": Wq + 1 / mu, "L": Lq + a}

Pregunta de control. En la tabla anterior, busca un cliente que sale antes que otro que llegó antes que él. ¿Es un error del código? ¿Se viola la disciplina FCFS?

Pista: FCFS dice en qué orden se empieza a atender, no en qué orden se termina (por eso no hablamos de FIFO, “primero en entrar, primero en salir”). Con \(s = 2\), un cliente con un servicio corto puede salir antes que uno que entró primero con un servicio largo. Con \(s = 1\) eso sería imposible.

Esto importa para el resto de la sección: una prueba de verificación tiene que valer para cualquier \(s\). Comprobar que “los fines de servicio salen en orden” es correcto con un servidor, pero con dos marcaría como error algo que no lo es.

¿Por qué np.allclose y no comparar a ojo o con ==?

  • Compara todos los valores de una vez y devuelve un solo True o False: basta con que una fila difiera para que dé False. Aquí son 6 clientes, pero la misma línea sirve para 6 000, donde revisar a ojo es imposible.

  • Solo compara números, posición por posición. No le importan los nombres de las columnas: en la tabla del simulador la columna se llama inicio y en nuestra lista esperado no tiene nombre, y aun así se pueden comparar. Lo que sí importa es el orden: compara el primer valor con el primero, el segundo con el segundo, etc. Por eso antes ordenamos la tabla por número de cliente.

  • Tolera los errores de redondeo. El computador guarda los decimales de forma aproximada: en Python, 0.1 + 0.2 == 0.3 da False. np.allclose(a, b) considera iguales dos números si su diferencia es menor que una tolerancia muy pequeña (por defecto, \(10^{-8}\) más \(10^{-5}\) veces el valor), así que no marca como error lo que es solo redondeo.

  • Queda escrita en el notebook. Cada vez que cambiemos el código podemos volver a correr la celda y saber en un segundo si algo se dañó.

Por eso es una herramienta muy útil para verificar: sirve siempre que el modelo conceptual diga que dos cantidades deben ser iguales. La volvemos a usar en la sección 3.3 para comprobar que fin = inicio + servicio en miles de clientes.

3.3 Invariantes: cosas que deben cumplirse siempre#

Un invariante es una propiedad que el modelo conceptual exige en cualquier corrida, sin importar la semilla ni los parámetros. Si alguna vez falla, hay un error. Agrupamos varios en una función para poder repetirlos cada vez que cambiemos el código:

def revisar_invariantes(res, clientes, eventos, s, tol=1e-9):
    # Recibe lo que devuelve simular_mms(..., traza=True) y revisa cada invariante.
    # Cada prueba produce un solo True (se cumple) o False (hay un error).
    # tol es un margen diminuto para que un error de redondeo no cuente como violación.

    # Tabla de clientes ordenada por hora de llegada (la usa la prueba de FCFS)
    por_llegada = clientes.sort_values("llegada")
    # Error relativo entre L, medido por área bajo N(t), y lam_efectiva * W, medido sobre clientes
    error_little = abs(res["L"] - res["lam_efectiva"] * res["W"]) / res["L"]

    chequeos = {
        # clientes[["espera", "servicio"]] >= -tol  -> tabla de True/False, una casilla por valor
        # el primer .all() revisa cada columna y el segundo junta las dos columnas en un solo valor
        "Ningún tiempo negativo": (clientes[["espera", "servicio"]] >= -tol).all().all(),
        "Nadie empieza antes de llegar": (clientes["inicio"] >= clientes["llegada"] - tol).all(),
        # np.allclose (sección 3.2): compara fin con inicio + servicio, cliente por cliente
        "fin = inicio + servicio": np.allclose(clientes["fin"], clientes["inicio"] + clientes["servicio"]),
        # .max() es el mayor número de clientes en servicio que aparece en toda la traza de eventos
        f"Nunca más de s = {s} en servicio": eventos["en_servicio"].max() <= s,
        # .is_monotonic_increasing es True si cada valor es mayor o igual que el anterior:
        # ordenados por llegada, nadie empieza a ser atendido antes que alguien que llegó primero
        "FCFS: inicios en orden de llegada": por_llegada["inicio"].is_monotonic_increasing,
        # aquí no hay columnas sino tres números sueltos, y son conteos enteros: no hay redondeo,
        # así que basta con ==. np.allclose(res["llegadas"], res["salidas"] + res["en_sistema_al_final"])
        # también funcionaría y daría lo mismo.
        "Conservación de clientes": res["llegadas"] == res["salidas"] + res["en_sistema_al_final"],
        "Ley de Little (error < 2%)": error_little < 0.02,
    }
    # Convierte el diccionario {nombre de la prueba: True/False} en una tabla de una columna
    return pd.Series(chequeos, name="¿se cumple?")

3.4 Contra la teoría: Erlang C y casos límite#

Como el modelo conceptual es una M/M/s, conocemos el valor exacto que el código debería producir en promedio. Una sola corrida no basta para compararlo (semana 5: una corrida es una sola observación), así que hacemos 10 réplicas con semillas distintas y usamos el intervalo de confianza \(t\) de la semana 3:

\[ \bar Y \pm t_{0.975,\,R-1}\,\frac{S}{\sqrt{R}} \]

donde ahora cada \(Y_j\) es el resultado de la réplica \(j\). Por qué es legítimo tratar cada réplica como una observación, y cuántas réplicas hacen falta, es justamente el tema de la semana 14; hoy lo usamos como herramienta.

Probamos \(s = 1, 2, 3\) con la misma utilización \(\rho = 0.8\). Como \(\rho = \lambda/(s\mu)\) depende de \(s\), para mantenerla en 0.8 aumentamos \(\lambda\) en la misma proporción que \(s\): con \(\mu = 1\) usamos \(\lambda = 0.8\,s\), es decir, \(\lambda = 0.8,\ 1.6\) y \(2.4\). Si dejáramos \(\lambda\) fijo, la utilización bajaría al agregar servidores. Así comparamos sistemas de distinto tamaño en los que cada servidor está igual de ocupado.

def ic_t(datos, confianza=0.95):
    # Intervalo t de la semana 3: devuelve (media, semiancho HW)
    datos = np.asarray(datos, dtype=float)
    R = len(datos)
    hw = stats.t.ppf((1 + confianza) / 2, R - 1) * datos.std(ddof=1) / np.sqrt(R)
    return datos.mean(), hw

def ks_bootstrap(x, dist, params, fit_kwargs=None, B=1000, seed=2026):
    # KS con p-value corregido por bootstrap paramétrico, igual que en la semana 12: como los parámetros
    # se estiman con los mismos datos, el p-value de kstest sale inflado.
    # Devuelve (D observada, p-value de kstest sin corregir, p-value corregido).
    fit_kwargs = fit_kwargs or {}
    x = np.asarray(x)
    rng = np.random.default_rng(seed)
    ks_obs = stats.kstest(x, dist.cdf, args=params)
    D_boot = np.empty(B)
    for b in range(B):
        y = dist.rvs(*params, size=len(x), random_state=rng)
        D_boot[b] = stats.kstest(y, dist.cdf, args=dist.fit(y, **fit_kwargs)).statistic
    return ks_obs.statistic, ks_obs.pvalue, np.mean(D_boot >= ks_obs.statistic)

def metricas_por_dia(tabla_clientes):
    # Una fila por día: .groupby("dia") junta los clientes de cada día y .agg(...) calcula, en cada grupo,
    #   atendidos = cuántas filas (clientes) tiene el día   -> ("espera", "size")
    #   Wq        = promedio de la espera del día            -> ("espera", "mean")
    return tabla_clientes.groupby("dia").agg(atendidos=("espera", "size"), Wq=("espera", "mean"))

def simular_dias(n_dias, pausa=None):

def comparar(real, modelo):
    # IC 95% (media ± HW) de cada métrica: cada día es una observación
    tabla = {}
    for metrica in ("atendidos", "Wq"):
        m_r, h_r = ic_t(real[metrica])
        m_m, h_m = ic_t(modelo[metrica])
        # Dos intervalos se traslapan si cada uno empieza antes de que termine el otro

        tabla[metrica] = {"sucursal (datos)": f"{m_r:.2f} ± {h_r:.2f}", "modelo": f"{m_m:.2f} ± {h_m:.2f}",
                          "¿los IC se traslapan?": se_traslapan}
    return pd.DataFrame(tabla).T

  • Espera promedio \(W_q\): el modelo predice bastante menos espera de la que viven los clientes, y los intervalos no se tocan.

Para la gerencia la métrica que importa es la espera, porque es la que cambia al cambiar el número de cajeros. Un modelo puede parecer válido en una métrica y fallar en la que importa: la validación se hace contra las salidas relevantes para la decisión, y contra más de una.

Aquí leemos los intervalos de forma descriptiva. Decidir formalmente si dos sistemas difieren (con la diferencia de medias, muestreo pareado, etc.) es el tema de la semana 16.

4.4 Juicio de expertos, corrección y calibración#

Le mostramos la gráfica a la gerencia y la respuesta es inmediata: un cajero sale a almorzar de 12:00 a 13:30. El supuesto 3 (“3 cajeros todo el día”) era falso, y ninguna prueba sobre los datos de entrada podía detectarlo. Lo corregimos con el parámetro pausa (minutos 240 a 330) y repetimos la comparación.

¿Cómo funciona la pausa? PriorityResource#

simpy.PriorityResource funciona como el Resource de las semanas 4 y 5, pero cada solicitud lleva un número priority: cuando un cajero se libera, pasa la solicitud con el número más bajo (si hay empate, la que llegó primero). Los clientes piden con priority=1 y el almuerzo con priority=0:

Qué pasa

11:59

12:01

13:30

Termina el almuerzo: el cajero vuelve a atender al siguiente de la fila.

Como es código nuevo, lo verificamos con la traza: durante la pausa no debería haber más de 2 clientes en servicio.

Tres ideas para cerrar la sección:

  • Juicio de expertos. Mostrarle salidas del modelo a quien conoce el sistema es una técnica de validación en sí misma. Revisar si los resultados “tienen sentido” se llama validez aparente (face validity). Una versión más exigente es la prueba de Turing: mezclar reportes del modelo y del sistema real y ver si el experto logra distinguirlos.

  • Calibrar no es corregir. Habríamos podido “arreglar” la diferencia subiendo el tiempo medio de servicio hasta que la espera cuadrara. Eso es calibrar, y aquí habría sido un error: \(\mu\) estaba bien estimado (sección 4.2), así que calibrarlo habría escondido el problema real. Ese modelo calibrado fallaría en cuanto la gerencia preguntara, por ejemplo, qué pasa si el almuerzo se mueve a las 15:00.

  • El orden importa. Verificamos primero. Si el código hubiera tenido un error, la discrepancia de la sección 4.3 podría haber sido culpa del código y no del supuesto, y habríamos buscado el problema en el lugar equivocado.

Resumen#

  1. Validar el ajuste, verificar y validar el modelo son tres preguntas distintas, con herramientas distintas. Ninguna reemplaza a las otras.

  2. Verificar es comparar el código contra el modelo conceptual: trazas, casos con tiempos fijos (con el mismo código, no con una copia), invariantes, conservación, Ley de Little y fórmulas exactas como Erlang C.

  3. Las pruebas deben valer para cualquier \(s\). Con varios servidores los clientes pueden salir en otro orden del que llegaron, y eso no viola la disciplina FCFS, que solo exige que empiecen a atenderse en orden de llegada.

  4. Comparar contra Erlang C sigue siendo verificación: dice que el código implementa bien una M/M/s, no que el sistema real sea una M/M/s.

  5. Validar es comparar el modelo contra el sistema real: supuestos, salidas observadas (midiendo igual en ambos) y juicio de expertos.

  6. Entradas bien ajustadas no garantizan un modelo válido. En la sucursal, llegadas y servicios pasaron KS y aun así faltaba algo estructural: el almuerzo de un cajero.

  7. Un modelo puede parecer válido en una métrica (clientes atendidos) y fallar en la que importa para la decisión (espera).

def simular_mms_companero(lam, mu, s, T, semilla=0):
    # Versión que escribió un compañero a partir del modelo de la semana 5.
    # Corre sin errores... ¿hace lo que debe?
    rng = np.random.default_rng(semilla)
    m = {"salidas": 0, "Wq": [], "W": [], "area_L": 0.0, "area_Lq": 0.0,
         "n_sist": 0, "n_cola": 0, "t_ult": 0.0}

    def actualizar_areas(env):
        dt = env.now - m["t_ult"]
        m["area_L"] += m["n_sist"] * dt
        m["area_Lq"] += m["n_cola"] * dt
        m["t_ult"] = env.now

    def cliente(env, servidores):
        t_llegada = env.now
        actualizar_areas(env)
        m["n_sist"] += 1; m["n_cola"] += 1
        with servidores.request() as turno:
            yield turno
            actualizar_areas(env)
            m["n_cola"] -= 1
            espera = env.now - t_llegada
            t_serv = rng.exponential(1 / (s * mu))
            yield env.timeout(t_serv)
        actualizar_areas(env)
        m["n_sist"] -= 1
        m["Wq"].append(espera)
        m["W"].append(espera + t_serv)
        m["salidas"] += 1

    def generador(env, servidores):
        while True:
            yield env.timeout(rng.exponential(1 / lam))
            env.process(cliente(env, servidores))

    env = simpy.Environment()
    servidores = simpy.Resource(env, capacity=s)
    env.process(generador(env, servidores))
    env.run(until=T)
    actualizar_areas(env)
    L, Lq = m["area_L"] / T, m["area_Lq"] / T
    return {"utilizacion": (L - Lq) / s, "Wq": statistics.mean(m["Wq"]),
            "W": statistics.mean(m["W"]), "Lq": Lq, "L": L,
            "lam_efectiva": m["salidas"] / T}
